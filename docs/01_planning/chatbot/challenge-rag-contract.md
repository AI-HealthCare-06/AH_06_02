# 챌린지 ↔ AI·RAG 연결 계약

정리: 배수빈 (D 후속 담당) · 2026-10-27 · 1단계 추천 챌린지 21개·대화형 지원 21개·승인 카드 48장·개인 목표 단계 반영

AI·RAG를 붙이기 전에 챌린지 쪽이 어디까지 만들었고, AI가 어느 자리에 들어와 무엇을 바꿀 수 있는지 정리한 문서다. 공개 API 형태는 연결하는 쪽에서 정한다.

## 1. 챌린지는 지금 이렇게 돈다

1단계 기능은 모두 운영 서버에서 돌고 있다.

```
예측 완료
  → 공략 대상 자동 선정: 위협도 1위 캐릭터 하나 (도감에서 변경 가능, CHLG-10)
  → 추천 생성 CHLG-01: 규칙으로 후보 최대 3장
  → 사용자가 고름: 시작 CHLG-05 / 거절·해당 없음 CHLG-03
  → 시작하면 28일 치 예정 기회(날짜 × 슬롯)를 미리 만든다
  → 수행 기록 CHLG-07: 서버 타이머 · 직접 체크 · 사진
  → 예정 기회가 인정 완료되면: 공략 점수 +10, XP, 보상 카드 뽑기 1회
  → D28 경계에서 같은 주기 챌린지가 함께 끝난다 (이월 없음)
```

### 추천 규칙 (`app/services/recommendations.py`)

- 후보는 아래 표의 1단계 추천 대상 중 공략 대상 캐릭터의 요인에 맞는 것만 쓴다.
- 점수는 미진단 질환이면 개인 SHAP을 P95로 나눈 값, 진단 질환이면 전역 중요도 × 생활행동 가중치다. 점수 순으로 최대 3장을 낸다.
- 진행 중이거나 쿨다운·수동 제외 중인 챌린지는 빠진다. 같은 챌린지를 3번 연속 거절하면 다시 추천받을 시점(7일 · 30일 · 직접 해제)을 고른다.
- 남은 슬롯이 없으면 추천을 만들지 않는다. 시작할 때 처음 최대 2개, D7부터 주기당 1개 더, 동시에 최대 3개다.

## 2. 1단계에서 끝난 것과 안 하는 것

**끝난 것**: 위 흐름 전체(CHLG-01\~14), 도감(MNSTR-01), 보상 카드·꾸미기·성장 아이템(RWRD-01\~07), 성장 기록(PROG-01), 캐릭터 4종의 단계별 그림 5장과 변화 도감 화면. 화면은 v5로 연결했고 운영 서버에서 확인했다.

**1단계에서 안 하는 것**

- 봉인 판정. 28일이 지나면 "기간 종료"로만 보여 준다
- 실제 서비스의 캐릭터 외형 변화(REQ-RECO-008). 체험 모드에서는 수행 5회마다 한 단계씩 바뀐다. 실제 서비스는 외형을 바꿀 기준이 아직 없어 서버가 단계 값(`seal_progress`)을 비워 보내고, 도감은 1단계로 두며 변화 도감은 미리보기로 보여 준다
- 습관 형성 판정. `habit_established`가 비어 있으면 "판정 안 함"이다
- 스파이크 위협도. 실측 혈당을 위협도로 바꾸는 기준이 아직 없다
- 수치 인증(value) 챌린지, 나트륨 계열 추천, 조건이 정해지지 않은 진단자 요인(음주·체격·활동)
- **대화형 추천(REQ-CHLG-012)**. 이 문서가 넘기는 범위다

## 3. AI·RAG가 들어올 자리

### 원칙

AI는 **서버가 정한 챌린지 코드 중에서 고르고 이유를 설명하는 일**만 한다(Select, not Generate). 새 챌린지, 목표량, 난이도, 단계, 점수, 기간, 요인은 만들지 않는다. 고른 챌린지의 값은 서버가 규칙·마스터로 채워 JSON으로 내려 주고, 시작은 사용자가 기존 CHLG-05로 한다. 2026-10-28부터 이 절의 결정은 최병주가 한다.

두 단계로 나눈다.

```
1단계 대화  POST /api/v1/challenge-chat
  사용자 자유 질문 → Page Index 검색(카드·챌린지·단계표) → gpt-4o 자유 대화
  → 답 문장만 돌려준다. 아무것도 저장하지 않는다. 대화 기록은 클라이언트가 들고 있다

2단계 선택  POST /api/v1/challenge-chat/select
  대화 기록 + 선택형 답변
  → 부족한 정보만 선택형 질문 (최대 3개, 이미 답한 건 생략)        → ask
  → 디시전 모델: JSON 스키마(코드·카드 enum, strict)로 최대 3개 선택, temperature 0
  → 서버 재검증 (스키마 + 코드·카드 유효성 + 이유 문장)
       통과  → conversation: 규칙이 정한 목표 값으로 추천 행을 만들어 서빙
       실패  → rules: 규칙 추천 그대로
       후보 없음 → hold: 추천 보류
  → 사용자가 서빙 JSON의 recommendation_id로 CHLG-05 시작
```

### 디시전 모델 출력 제한

출력 스키마는 요청마다 만든다. `selections` 배열(최대 3개)의 각 항목은 코드마다 한 갈래(`anyOf`)이고, 갈래마다 `challenge_code`는 그 코드 하나, `evidence_card_ids`는 그 코드의 승인 카드 ID만 enum으로 허용한다. 다른 챌린지의 카드를 붙이거나 목표 값 키를 넣는 출력은 토큰으로 나올 수 없다(OpenAI Structured Outputs `strict`).

```json
{"selections": [{"challenge_code": "CH_WALK_AFTER_MEAL", "evidence_card_ids": ["C01"], "reason": "..."}]}
```

서버는 받은 값을 다시 검사하고, 하나라도 어긋나면 전체를 버리고 `rules`로 돌아간다.

- `challenge_code`: 1단계 추천 대상 21개(`SUPPORTED_CODES`) 안이고, 이번 요청에서 고를 수 있는 코드이며, 중복이 없어야 한다
- `evidence_card_ids`: 이번 요청에 보낸 승인 카드이고, 같은 챌린지의 카드여야 한다
- 그 밖의 키: 받지 않는다(`extra=forbid`)

### 이유 문장

이유 문장(`reason`)이 아래를 모두 지키면 그대로 보여 준다. 하나라도 어기면 선택은 살리고 문장만 고정 문장 **"대화 내용에 맞춰 골랐어요."**로 바꾼다. 카드 원문(`guidance`)은 운영 기준 말투라 사용자에게 보여 주지 않는다.

| 검사 | 기준 |
| --- | --- |
| 숫자 | 그 챌린지에 서빙하는 목표량(`target_value`)·하루 횟수(`daily_target_count`)와 같은 숫자만 허용 |
| 운영자 말투 | "\~라고 답한 경우", "\~를 제안한다" 같은 카드 원문 말투가 없을 것 |
| 단정 표현 | 질환 치료·예방·수치 개선·위험도·진단을 말하지 않을 것 |

바꿨는지는 `conversation_snapshot.reason_replaced`에 남는다. 1단계 대화 답도 단정 표현이 있으면 고정 안내 문장으로 바꾼다.

### 고를 수 있는 코드

| 단계 | 개수 |
| --- | --- |
| 1단계 추천 대상 | 21개 |
| 공략 대상 캐릭터에 맞는 후보 | 비세라 13 · 알데 4 · 코티니 4 · 스파이크 0 |
| 디시전 모델 enum | 그중 진행 중·쉬는 기간이 아니고, 사용자가 "가능하다"고 답했고, 승인 카드가 문맥에 들어간 코드 |
| 한 번에 고르는 수 | 최대 3개 |

- 규칙 추천의 상위 3장으로 좁히지 않는다. 대화 내용에 맞는 코드를 고를 수 있게 공략 대상 후보 전체를 넘긴다. 문맥 카드는 최대 12장이라 코드마다 한 장을 먼저 넣는다.
- 공략 대상 캐릭터의 요인이 아닌 코드(예: 대상이 비세라일 때 흡연 챌린지)는 대화에서 원해도 고를 수 없다.
- 시작할 수 있는 수는 따로 제한된다. 처음 2개, D7부터 1개 더, 동시에 최대 3개다.

### 주고받는 값

| 방향 | 내용 |
| --- | --- |
| 서버 → LLM (1단계) | 대화 기록(가린 뒤), 후보 코드·제목·상황·서빙 목표, 검색된 페이지 |
| 서버 → LLM (2단계) | 대화 기록(가린 뒤), 선택형 답변, 캐릭터 코호트 범주(상태·진행 중 단계·지난 수행률 구간), 후보와 서빙 목표(읽기 전용), 승인 카드 |
| 가리고 보냄 | 대화 속 이메일·전화번호·6자리 이상 숫자는 `[생략]`으로 바꾼다 |
| 보내지 않음 | 이름 · 이메일(계정) · 건강 수치 · 예측 확률 · 진단 기록 |
| LLM이 정하지 않음 | 사용자 · 주기 · 공략 대상 · 모델 점수 · 목표 값 · 단계. 모두 서버가 정한다 |
| LLM → 서버 | 1단계: 답 문장 / 2단계: 위 스키마의 `challenge_code`, `evidence_card_ids`, `reason` |

LLM 호출이 실패하거나(키 없음·키 오류·시간 초과) 응답이 검증을 못 넘으면 오류를 내지 않는다. 1단계는 고정 안내 문장, 2단계는 `rules`로 돌아간다. 로그에는 예외 종류와 HTTP 상태만 남기고 키·본문은 남기지 않는다.

### 저장

새 테이블이나 컬럼은 만들지 않는다. 2단계에서 고른 것만 `challenge_recommendations`에 새 행으로 저장하고, 이미 있는 세 칸을 쓴다. 1단계 대화는 저장하지 않는다.

| 컬럼 | 넣는 값 |
| --- | --- |
| `conversation_snapshot` | `policy_version`(`RAG-CHAT-20261028-v2`) · `fingerprint` · `answers` · `asked` · `card_versions` · `model_version`(예측 모델) · `health_record_id` · `reason` · `reason_replaced` |
| `llm_model_version` | 선택에 쓴 LLM 식별자 (32자 이내, 예: `gpt-4o`) |
| `evidence_card_ids` | 근거로 쓴 승인 카드 ID 배열 (`C01`\~`C48`) |

- `source_type`은 원래 값(`prediction_personal` · `diagnosis_global`)을 그대로 둔다. 대화를 거쳤다고 `conversation`으로 바꾸지 않는다 (10/13 A·D 합의).
- `proposed_goal`은 규칙 추천이 정한 개인 목표 단계다(5절). 대화형 추천도 같은 값을 넣는다.
- 같은 사용자·주기·건강기록·모델·카드 버전·대화·답변으로 다시 부르면 처음 저장한 결과를 돌려준다.

### 설정

| 환경 변수 | 기본 | 뜻 |
| --- | --- | --- |
| `CHALLENGE_CHAT_ENABLED` | `false` | 켜고 키가 있어야 LLM을 부른다. 아니면 1단계 `off`, 2단계 `rules` |
| `OPENAI_API_KEY` | 빈 값 | 로컬은 루트 `.env`(= `envs/.local.env`), 운영 서버는 `~/project/.env`. 예시 파일에는 넣지 않는다 |
| `OPENAI_MODEL` | `gpt-4o` | 32자 이내 |

키를 넣은 뒤 확인: `uv run python -m scripts.rag.check_openai [--base-url http://localhost:8000]`. 설정이 어긋나면 서버 시작 로그에 키 값 없이 경고를 남긴다.

### 카드를 늘리거나 고칠 때

- 근거 출처는 `https://www.who.int/` 주소만 허용한다. 페이지에 실제로 있는 문장만 근거로 쓰고, 목표량·횟수는 팀 운영 기준이라고 `policy_note`에 적는다.
- 지원 코드를 늘리면 질문(`QUESTION_TEXT`), 목표 고정 표(`FIXED_GOALS`), 승인 카드를 함께 넣어야 한다. 셋 중 하나가 빠지면 테스트가 실패한다.

임베딩이나 벡터 DB 없이 작은 카드 묶음을 태그로 검색하는 방식이다. 검색 방식은 바꿔도 되지만, 위 입출력과 검증은 지킨다.

새 챌린지 만들기, 목표량·난이도·단계·점수 바꾸기, 위험도·위협도를 말하거나 진단처럼 말하기는 자동화하지 않는다.

## 4. 연결 전에 정한 것

카드 초안(`challenge-cards-20261002.md`) 8절에서 연결 전에 팀이 확인하자고 한 네 항목을 아래처럼 정했다.

| 항목 | 1단계 결정 |
| --- | --- |
| 사용할 키 | 1단계 추천 대상 21개 전부. 걷기·좌식만이 아니다 |
| 조정 범위 | 챌린지별 단계표 안에서만 바꾼다(5절). 단계표 밖 값은 시작할 때 거절한다 |
| 근거 카드 | C01\~C48. 카드마다 WHO 출처·원문 위치·검토일이 있고, 코드별 질문과 선택 규칙에 연결돼 있다 |
| 유지 정책 | 7일 점검 화면은 없다. 계속은 그대로 진행, 조정은 다음 주기 추천이 지난 주기 수행률로 한다(5절). 교체는 중단(CHLG-09)한 뒤 남은 슬롯으로 새로 시작한다. D7부터는 주기당 1개만 더 시작할 수 있다. 28일이 끝나면 다음 주기에 추천을 새로 받는다. 같은 챌린지가 다시 후보로 나올 수 있고, 지금 대화형 추천은 지난 주기 기록을 보지 않고 새 후보 안에서만 고른다 |

자동 누적, 졸업 판정, 봉인 연출은 1단계에서 하지 않는다.

## 5. 개인 목표 단계

### 단계표

챌린지마다 허용 단계를 `challenges.personalization_policy`에 둔다. 원본은 [`../challenge-master.csv`](../challenge-master.csv)이고 시드가 넣는다. 새 칼럼은 없다.

- 기본 단계는 마스터 목표와 같다. 시드가 어긋난 단계표를 거부한다.
- 하루 XP는 단계 난이도로 서버가 정한다. easy 12 · normal 24 · challenge 36 (10/6 합의).
- 강도는 단계 문구로만 붙인다. 앱이 강도를 잴 수 없어서 시간·횟수만 타이머와 횟수로 확인한다.
- `status`가 `approved`인 단계표만 쓴다. 단계표가 없으면 지금처럼 마스터 목표로만 시작한다.

| 챌린지 | 단계 (굵게 = 기본) |
| --- | --- |
| 식후 걷기 | 10분 하루 1회(easy) → 20분 하루 1회(normal) → **점심·저녁 10분씩(challenge)** → 점심·저녁 20분씩(challenge) → 점심·저녁 20분씩 빠른 걸음(challenge) |
| 업무 중 움직임 휴식 | 3분 1회(easy) → 3분 2회(normal) → **3분 3회(challenge)** |
| 맨몸 근력 | **10분(normal)** → 20분(challenge) → 30분(challenge) |
| 저녁 걷기 | 10분(easy) → **20분(normal)** → 30분(challenge) → 30분 빠른 걸음(challenge) |
| 집안일로 몸 움직이기 | **15분(easy)** → 20분(normal) → 30분(challenge) |
| 스쿼트 | 의자 짚고 15회(easy) → **15회(normal)** → 20회(challenge) |
| 벽 짚고 팔굽혀펴기 | **10회(easy)** → 15회(normal) → 20회(challenge) |
| 영상 볼 때 일어나기 | 1시간마다(easy) → **30분마다(normal)** |
| 아침 첫 담배 미루기 | 15분(easy) → **30분(normal)** → 1시간(challenge) |

나머지 12개는 단계표가 없다. 하루 1회 직접 확인하는 챌린지라 바꿀 값이 없다.

움직임 휴식의 단계는 10/6 합의 조합(`../challenge-candidates.md`)이다. 나머지 8개 챌린지의 단계는 2026-10-28 배수빈이 확정했다. 하루 1회 식후 걷기는 슬롯을 정하지 않고 아무 식사 뒤에 해도 된다.

### 다음 주기 단계

추천을 만들 때(CHLG-01) 같은 챌린지의 지난 주기 결과를 본다. 기준은 기간 종료로 끝난 가장 최근 미션의 수행률(인정 완료 ÷ 예정 기회)이다.

| 지난 주기 수행률 | 다음 추천 |
| --- | --- |
| 80% 이상 | 한 단계 위. 가장 높은 단계면 유지 |
| 50% 이상 80% 미만 | 같은 단계 |
| 50% 미만 | 한 단계 아래. 가장 낮은 단계면 그 단계로 두고 다른 챌린지를 먼저 보여 준다 |

- 수행률이 없는 미션(예정 기회 0)은 근거로 쓰지 않는다.
- 같은 주기에 한 번 시작했던 챌린지는 처음 단계를 그대로 제안한다. 다른 단계로는 다시 시작할 수 없다. 같은 날 하루 횟수가 바뀌면 이미 받은 XP와 새 목표가 섞이기 때문이다.
- 놓친 날로 점수를 깎지 않는다. 단계가 내려가면 하루 XP와 하루에 쌓이는 `공략 점수`가 함께 줄 뿐이다. `공략 점수`는 인정 완료 1회마다 마스터 `progress_value`만큼 오른다.
- `위험도`·`위협도`는 단계와 관계없다.

### 저장과 시작

`proposed_goal`에는 단계 값이 아니라 단계 번호와 근거만 넣는다. 값은 시작할 때 단계표에서 다시 꺼낸다.

```json
{
  "policy_version": "P1-STEPS-20261027",
  "level": 3,
  "basis": {"user_challenge_id": 12, "completion_rate": "0.8500", "previous_level": 2, "direction": "up"}
}
```

- 시작(CHLG-05)할 때 단계표 버전이 다르거나 없는 단계면 `VALIDATION_ERROR`로 거절하고 "추천을 다시 받아 주세요"라고 안내한다. 마스터 목표로 바꿔 시작하지 않는다.
- 지난 단계보다 올린 목표는 마스터 값과 관계없이 시작 전에 안전 확인(`safety_confirmed`)을 받는다. 추천 응답의 `safety_check_required`가 `true`로 내려가 화면이 확인 칸을 띄운다.
- 시작하면 `goal_config_snapshot`에 `level` · `policy_version` · `title` · `intensity` · `context_slots` · `basis`를 남긴다. 기본 단계로 시작해도 남긴다. 그 뒤 기록·타이머·슬롯 검사는 이 스냅샷을 따른다.
- 추천 응답과 진행 중 목록은 단계의 제목·목표·난이도·XP를 보여 주고, `intensity` · `goal_level` · `goal_basis`를 더 내려 준다.

### AI가 단계를 고를 때

지금 대화형 추천은 단계를 바꾸지 않는다. "쉽다·힘들다" 답으로 단계를 바꾸려면 LLM이 단계 번호만 고르고, 서버가 위 단계표·기준·안전 확인 규칙으로 다시 검사한다. 단계를 올리는 쪽은 수행률 기준과 안전 확인을 함께 넘어야 한다.
