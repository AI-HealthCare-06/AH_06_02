# 공략 도우미 질문 방식 재설계안

작성 2026-10-31 · 2026-11-01 병주님 승인(7절 여섯 결정 모두 권장안) · 구현 `feature/chat-question-decision`

## 1. 출발점

병주님 구상

1. 질문지를 코드에 하드코딩하지 않는다
2. 질문지를 페이지 인덱스에서 랜덤으로 뽑는다
3. 사용자는 선택지를 눌러 넘어간다(객관식)
4. 전체 답변을 보고 챌린지를 고른다

레퍼런스: DecisionRAG(arXiv 2610.35868, Cornell·ASAPP, 2026-10-31 공개, 국내 정리 글 기준). 결과 수치는 논문 측 보고이고 따로 검증하지 않았다.

| 질문 고르기 | 사전 순서 앞 3개, 고정 | 페이지 인덱스에서 랜덤 | 판단 모델이 가지를 평가해 좁힘 |
| 시작 방식 | 자유 입력 필수, 답을 받은 뒤 '고르기' | 선택지 클릭부터 | — |
| 검색(Retriever) | 태그 부분 일치 점수. 사용자 말이 태그에 안 걸리면 0건 | — | 검색 모델 없이 LLM 판단으로 탐색 |

| 최종 선택 | gpt-4o 가 strict JSON 스키마(코드·카드 enum)로 **토큰을 생성**해 최대 3개 + 이유 문장 | 전체 답변을 보고 선택 | 정해진 선택지에 대한 **확률 분포**만 낸다. 토큰 생성 없음 |
| 재현성 | temperature 0 + 같은 입력 캐시 | — | 확률 argmax 라 같은 입력이면 같은 결과 |

지금의 '디시전 모델'은 출력 범위를 enum 으로 막은 생성 모델이다. 고를 수 있는 값은 막혀 있지만 이유 문장을 쓰고, 확률은 내지 않는다. DecisionRAG 의 디시전 모델과는 다르다.

## 3. 누가 고르는가 — 사용자 클릭과 모델 판단을 나눈다

| 단계 | 고르는 주체 | 방식 |
| --- | --- | --- |
| 질문에 답하기 | **사용자** | 선택지 클릭(객관식). 사용자의 Multiple-Choice |
| 답으로 후보 지우기 | **서버 규칙** | '어려워요'·'아니요'면 그 챌린지 가지를 닫는다. 몸 상태 제한이면 보류. LLM 불필요 |
| 다음 질문 고르기 | **서버(랜덤) + 모델(선택)** | 살아 있는 가지 안에서 질문 페이지를 랜덤으로 뽑는다. 가지가 많을 때만 판단 모델이 가지별 Yes/No 로 먼저 좁힌다 |
| 자유 입력 해석(선택) | **모델** | Parallel Binary: 살아 있는 챌린지마다 "이 말에 맞는가"를 Yes/No 확률로. 태그 검색을 대신한다 |
| 최종 챌린지 | **모델** | 살아 있는 챌린지 중 Multiple-Choice(확률 합 1) 또는 Binary 확률 상위 3개. 서버가 목표 값을 채운다(지금과 같음) |

DecisionRAG 의 Multiple-Choice 는 **모델이 후보 중 하나를 고르는 판단 방식**이고, 화면의 '선택지 클릭'은 **사용자 입력**이다. 둘은 다른 층이다. 사용자 클릭 결과가 모델 판단의 입력(전체 답변)이 된다.

## 4. 재설계 흐름

### 4-1. 트리로 만든 페이지 인덱스

```
L0 공략 대상 캐릭터 (위험도 모델·규칙이 이미 정함)   비세라 · 알데 · 코티니
L1 요인 factor_key                                   bmi_high · physical_activity_low · ...
L2 챌린지 (1단계 지원 21개)                          식후 걷기 · 계단 오르기 · ...
L3 페이지                                            질문 페이지 · 근거 카드 · 단계표
```

- **질문 페이지(새로 추가)**: 질문 문장, 선택지, 답 → 가지 처리 규칙(유지·닫기·보류). 코드 dict 대신 데이터 파일(예: `docs/01_planning/chatbot/questions-YYYYMMDD.json`)로 두고 인덱스가 읽는다. 원래 기획(rag-plan §7)의 카드 '확인 질문' 항목을 되살리는 것과 같다
- 챌린지 하나에 질문 페이지를 여러 개(표현·관점이 다른 것) 둘 수 있어야 랜덤이 의미가 있다

### 4-2. 화면 흐름(클릭 먼저)

1. 공략 도우미를 열면 바로 1번 질문 말풍선 + 선택지 칩. 자유 입력은 아래에 선택으로 남긴다
2. 답할 때마다 서버 규칙이 가지를 닫고, 살아 있는 가지에서 다음 질문을 랜덤으로 뽑는다(한 번에 한 질문)
3. 질문 예산(기본 3개, 결정 필요)을 다 쓰거나 남은 후보가 3개 이하이면 멈춘다
4. 전체 답변(+ 자유 입력이 있으면 그것까지)으로 판단 모델이 최종 3개를 고른다 → 지금처럼 결과 카드 → 상세 → 시작
5. 판단 실패·키 오류면 지금처럼 규칙 추천(`rules`), 몸 상태 제한이면 `hold`

### 4-3. 랜덤

- 시드는 사용자·주기·질문 차례로 고정한다. 같은 사람이 같은 주기에 다시 열면 같은 질문이 나온다(요구사항 "같은 입력이면 같은 결과", `requirements.md` 385행)
- 다른 주기·다른 사용자에게는 다른 질문이 나온다

### 4-4. 판단 모델 구현

DecisionRAG 원형은 로짓에 접근해 한 번의 forward pass 로 선택지 확률을 낸다(논문은 8B 모델 사용). gpt-4o API 로는 그대로 할 수 없어 근사한다.

| 안 | 방식 | 장단점 |
| --- | --- | --- |
| A (권장) | 후보에 A·B·C… 한 글자 라벨을 붙이고 출력 1토큰 + `logprobs`(상위 20개)로 확률을 읽는다 | 지금 공급자(gpt-4o) 유지, 생성 없이 확률·순위. 후보 20개 이하라 한 번에 된다(지금 최대 21개). Responses API 에서 logprobs 옵션을 쓸 수 있는지 로컬 확인 필요 |
| B | 지금처럼 strict JSON 생성 유지, 질문 흐름만 바꾼다 | 변경 적음. 확률·순위 없음, 이유 문장 생성 유지 |
| C | 오픈 웨이트 8B 를 직접 띄워 로짓 사용 | 원형에 가장 가깝다. 서버·GPU 부담이 커 지금 범위 밖 |

이유 문장: 확률만 내는 방식(A)은 문장을 만들지 않는다. 고른 이유는 **사용자 답 + 근거 카드 안내문으로 서버가 템플릿으로 채운다**(권장). 생성 문장을 유지하려면 고른 뒤 별도 호출로 쓰고 지금의 안전 검사를 그대로 건다.

## 5. 우리 규모에서의 판단

- DecisionRAG 의 큰 이점(34\~145배 속도, 268만 문단 탐색)은 큰 코퍼스용이다. 당고킬러 후보는 캐릭터당 챌린지 최대 10여 개, 지원 키 21개, 카드 48장이라 트리 탐색 없이도 후보 전체를 한 번에 판단할 수 있다
- 그래도 가져올 가치가 있는 것: (1) 태그 검색 대신 **LLM 판단으로 후보를 거른다**(사용자 말이 태그에 안 걸려도 놓치지 않음), (2) **확률로 순위**를 매겨 재현 가능하게 고른다, (3) 문장 생성이 없어 **이유·수치 환각 위험이 줄어든다**
- 트리 구조는 탐색 속도보다 **질문 페이지를 가지별로 관리·랜덤 추출**하는 데 쓴다

## 7. 결정(2026-11-01 승인)

1. 랜덤 생성: 인덱스에 저장된 질문 페이지에서 랜덤 추출
2. 자유 대화: 질문 뒤 선택 입력으로 유지
3. 질문 수: 최대 3개
4. 랜덤 재현성: 사용자·주기마다 고정
5. 판단 모델: A안 logprobs 확률 판단
6. 이유 문장: 서버가 채움. 카드 원문은 운영자 말투라 그대로 보여 줄 수 없어(기존 검사 `OPERATOR_PATTERN`), 사용자가 고른 답의 질문 페이지 문장을 쓰고 카드는 근거로 붙인다

## 8. 구현 메모

- 답 키·후보 규칙(`SituationAnswers`)은 그대로 두고, 질문 문장·선택지·이유 문장만 데이터로 옮겼다(`questions-20261101.json`, 답 키 21개 × 표현 2개). 기존 대화형 추천(`ConversationRecommendationService`)과 고정 평가는 답 키마다 첫 페이지를 쓴다
- 후보는 질문에 '할 수 있어요'로 답한 챌린지뿐이라 최대 3개다. 판단 모델은 이 안에서 순위를 매긴다. 후보가 1개면 모델을 부르지 않는다
- Responses API 의 logprobs(`top_logprobs` + `include: message.output_text.logprobs`)는 로컬 가짜 서버로만 확인했다. 키 교체 뒤 `uv run python -m scripts.rag.check_openai` 2단계로 실제 응답을 확인한다
