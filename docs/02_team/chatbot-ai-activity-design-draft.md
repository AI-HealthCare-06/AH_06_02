# 공략 도우미 AI 질의와 운동 범위 설계 초안

작성: 2026-11-02. 구현과 검증 전 초안이다.

## 목적과 경계

검사 뒤 처음 들어온 사용자가 선택지로 운동 환경과 수행 가능 범위를 답한다. 챌린지는 기존 21개만 사용하고, 한 공략 주기는 기존처럼 한 캐릭터를 대상으로 한다. 질문의 문구와 순서는 AI가 생성하되 선택지의 의미와 챌린지 연결은 서버가 통제한다. 운동 범위는 사용자가 답한 활동 가능 범위이며 질환 진단이나 의학적 운동 허가가 아니다.

## 운동 범위

| 범위 | 예시 | 판정에 필요한 답 |
| --- | --- | --- |
| 1 | 앉았다 일어나기, 가벼운 스트레칭 | 제한된 공간에서 가벼운 움직임을 할 수 있다고 명시 |
| 2 | 산책 | 야외 이동과 걷기가 가능하다고 명시 |
| 3 | 조깅, 팔굽혀펴기 | 공간과 체력의 여유가 있고 해당 활동을 할 수 있다고 명시 |

예시 자체를 새 챌린지로 만들지 않는다. 답이 없거나 모호한 경우 높은 단계로 추정하지 않는다. 몸 상태 때문에 어렵다는 답은 기존처럼 보류한다. 각 챌린지가 요구하는 범위와 개별 수행 가능 답의 관계는 코드별로 명시하고 검증해야 한다. 걷기 가능 답만으로 계단이나 근력 운동이 가능하다고 가정하지 않는다. 운동과 무관한 음주·흡연·식습관 챌린지는 운동 범위만으로 제외하지 않는다.

## 흐름과 데이터

1. 서버가 검사와 위험요인에서 양의 점수가 있는 요인을 확인하고 몬스터별 `factor_keys`와 교차한다. 공략 대상과 추천 저장은 기존 단일 캐릭터 주기 및 슬롯 규칙을 유지한다. 스파이크에 활성 추천이 없으면 챌린지를 만들어 내지 않는다.
2. 최초 검사 완료 뒤 바로 선택형 질문 화면으로 진입한다. 최초 여부는 서버의 기존 기록으로 확인하고 새로고침·재측정·기존 주기 사용자를 구별해야 한다.
3. 서버가 고정 질문 의도, 허용 답 값과 해당 후보 코드만 전달한다. AI는 문구와 선택지 표현 및 순서만 생성한다. 답변 이력은 선택된 범주만 전달하며 이름·건강 수치·진단·예측 확률은 보내지 않는다.
4. 기본 3문항을 묻는다. 수행 가능 여부가 불명확하거나 서로 모순되면 확인 질문을 추가하며 총 5문항을 넘기지 않는다. 다섯 문항 뒤에도 불명확하면 가능한 범위를 추정하지 않고 보류하거나 확인된 후보만 사용한다.
5. 최종 추천은 서버가 실제 답, 위험요인, 대상 몬스터, 활성 상태, 쿨다운, 승인 카드, 기존 목표 단계와 슬롯을 다시 검사한다. AI가 보낸 코드나 순위는 이 검사를 우회하지 못한다.

## 생성 검증과 실패 처리

생성 결과는 JSON 스키마로 받고 텍스트 길이, 질문 의도, 선택지 개수와 중복, 값 집합, 코드 집합을 서버에서 검사한다. 값은 서버가 제공한 집합과 정확히 같아야 하며, 사용자에게 보낸 문항과 답의 연결을 서버에서 검증할 수 있어야 한다. 모델이 생성한 문구가 답 값의 의미를 바꾸거나 치료·예방·위험도 개선을 단정하지 않도록 검증과 실패 시 처리가 필요하다. 토큰·키·요청 본문은 기록하지 않는다.

호출 실패, 시간 초과, 스키마 또는 의미 검증 실패 시 기존 42개 고정 질문으로 폴백한다. 폴백에서도 몸 상태 제한과 운동 범위 확인은 우회하지 않는다. 기존 질문만으로 범위를 확인할 수 없을 때는 확인되지 않은 운동 챌린지를 추정해 추천하지 않는다.

## 구현 전에 확정할 항목

- 21개 중 각 운동 챌린지의 최소 범위와, 각 범위에서 별도로 필요한 직접 확인 답.
- AI 생성 문구의 의미가 고정 답 값과 일치하는지 검증하는 방식과 실패 기준.
- 생성된 질문과 사용자 클릭을 서버에서 연결하는 상태 관리 방식 및 재요청·위변조 처리.
- 전체 E2E에서 실제 인증부터 검사·예측·질문·추천·시작까지 사용할 격리된 데이터와 서비스 환경.

현재 `POST /challenge-chat/select`는 고정 필드 답과 최대 3개 질문 키만 수용하고, 추천 후보는 `RecommendationService.eligible`에서 단일 주기 대상에 결합된다. 새 흐름은 이 계약과 테스트를 함께 바꿔야 한다.
